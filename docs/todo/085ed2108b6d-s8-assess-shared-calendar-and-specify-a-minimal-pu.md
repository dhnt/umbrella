Inspect all existing app/example/schedule capabilities first. Current schedule command is command automation; determine whether a shared human calendar exists elsewhere. Calendar should reference existing Session/Klatch/KB entities and use existing store/ref/access conventions. MVP needs shared dated sessions, timezone-aware display, participant access and links to materials. Recurrence and per-occurrence exceptions are optional follow-ups unless already available at negligible integration cost. Scheduling must not implicitly launch agents. Prefer existing functionality; if genuinely missing, assess a small pure-Go backend with browser UI and Git-managed durable event definitions, recording minimum dependencies and implementation stories. Reminder automation may reuse schedule but must be explicit. Acceptance: evidence-backed reuse/build decision and bounded MVP follow-up; no full calendar build, deployment or third-party integration undertaken in this discovery story.

Cross-cutting operator requirement: all Bashy apps/features must support software shaping and follow 'rod, not fish'. Prefer one reusable Bash# (.bsh) command/skill/script wrapper composing existing verbs and external tools; keep each underlying operation independently usable. Put variable behavior in templates/config/formats and name the shaping hook. Write new Go only for a necessary missing primitive/backend, not orchestration that Bash# can express. No one-off classroom, competition, roster or provider coupling. Reuse [[kb:bashy/extend-bashy-small-verbs-bash-skill-scripts-shaping-hooks-and-th]]. Acceptance includes the documented shaping hook and reusable wrapper/contract evidence; discovery stories specify these rather than implementing them.

Agent-first CLI parity (operator requirement): everything a human can see or do in an app, including all administration and management, must also be available through Bashy CLI under equivalent identity, permissions and approval rules. Provide discoverable help, scriptable/noninteractive inputs, structured outputs, stable entity references and actionable errors. Prefer Bash# command/skill wrappers over existing APIs/verbs. A browser-only action or a raw API with no Bashy CLI entry is an integration gap. S1 audits the UI-to-CLI action matrix; S6 verifies equivalent read results and state changes through browser and CLI, including denied access; S7/S8 must include full user/admin CLI coverage in their adapter/MVP decisions. Existing supported CLI paths are reused rather than rebuilt.

Memos reuse-first clarification: Memos already provides a calendar view. Official https://usememos.com/docs/usage/memos documents a month/day view grouping notes by creation/update timestamps, not due dates or meeting events. Upstream main contains web/src/components/CalendarView (CalendarView.tsx, CalendarGrid.tsx, useMonthMemos.ts), ActivityCalendar and calendar utilities. These React/TypeScript components depend on Memos contexts, memo APIs, routing and styling; they are not a standalone Go calendar engine.

Evaluate in order: (1) use the existing Memos calendar unchanged for dated notes; (2) adapt/reuse its view with a thin Bash# CLI/API wrapper where this satisfies the session scheduling requirement; (3) carve out a small reusable UI component only if dependency and maintenance costs justify it; (4) add only missing scheduling primitives. Explicitly distinguish memo create/update time from event start/end, timezone, recurrence and cancellation; do not encode scheduling by falsifying memo timestamps. A pure-Go backend can serve built browser assets; the UI need not be Go. Pin the evaluated source/release and preserve upstream license notices for any extraction. Record reuse versus extraction evidence and full CLI parity/shaping hooks before proposing implementation. No calendar coding in this session.

Operator priority clarification (supersedes earlier feature breadth and Memos-first ordering): choose the fastest implementation with the least total integration and maintenance effort. No preferred upstream. Compare reuse/adaptation against a tiny app composed from existing Bashy/Desk primitives; do not force third-party adoption or Memos extraction if that costs more. Shortlist from preliminary research: https://github.com/mgnsk/calendar (Go web event calendar), https://github.com/DouglasdeMoura/chroncal (Go CLI/TUI and CalDAV client), https://github.com/revelaction/ical-git (Go Git/local ICS reminder daemon). Their top-level licenses were checked as MIT; builds, dependency licensing and full access/CLI coverage remain unverified. Do not combine multiple calendar products merely to obtain every feature.

Minimum usable scope: create/list/show/edit/cancel dated events with title, start/end and explicit timezone; a shared agenda with event details; audience enforced using existing Bashy identity/access mechanisms; references to Session/Klatch/KB materials; durable local storage with the suite's explicit Git save/publish conventions. A month grid is optional if a simple agenda is faster. Every user/admin action must have a discoverable Bashy CLI path with structured output. One reusable Bash# skill/script wrapper composes existing verbs or the chosen API; UI templates/config and wrapper behavior provide explicit software-shaping hooks. Never hard-code a classroom or competition flow.

Defer recurrence, invitations/RSVP, reminders, CalDAV, external calendar sync, drag-and-drop, advanced views and Memos-specific UI extraction unless already supported with negligible added integration cost. Existing schedule automation remains separate; creating an event never starts agents implicitly. Acceptance for this discovery story: choose one smallest viable route using evidence, record gaps and a short bounded implementation follow-up. This session remains planning only; no coding or deployment.

Audience/interface requirement: Bashy is built for agentic tools to easily discover, use and manage all features through its CLI. Humans can also run the same CLI normally; it is not agent-exclusive, although human-oriented ergonomics are not its design priority. Bashy app/* web interfaces are designed to be human-friendly. Every web-visible capability and management action must have equivalent Bashy CLI support, with the same entities, permissions and approval rules. Agents may also inspect or operate web apps using bashy browser --live, REST APIs or web URLs; these are valid alternative paths, but can be more cumbersome or error-prone and do not substitute for CLI parity. Prioritize agent usability, discoverable help, scriptable/composable operations, structured inputs/outputs and actionable errors. Human TUI polish is not required; a CLI-only calendar does not supply the human-friendly web app.

Placement and graduation requirement: Calendar and Notes/Memos integrations start under bashy/examples/ as independently usable, software-shapeable examples with Bash# command/skill/script wrappers. They are not linked into or made required dependencies of the Bashy core. Reuse existing example registration, app hosting and contract patterns. Graduation is examples -> optional add-on -> foundation/core, following the existing evidence and platform/license/build requirements; this sprint does not authorize automatic graduation. Discovery recommendations and any implementation follow-up must state example-level placement. See [[kb:bashy/extend-bashy-small-verbs-bash-skill-scripts-shaping-hooks-and-th]].

Local-hosted calendar with cloud interop (operator decision): the delivered calendar is self-hosted and is the source of truth for events; a cloud provider is never required. Cloud calendars integrate only through explicit, user-invoked import/export: ICS (RFC 5545) file import/export as the provider-neutral baseline, plus cloud routes that compose existing examples — examples/google already exposes Google Calendar list/create through the gws-backed Bash# wrapper (google.bsh), so Google import/export reuses it rather than adding a client. Include examples/google in the existing-capability inventory and record why it is an interop route, not the shared calendar (provider-coupled, external account). Two-way sync, CalDAV serving and background sync stay deferred. Every import/export is a Bashy CLI operation with --dry-run, --json and the same audience checks; imported events record their source (provider/file and external UID) so re-import is idempotent.
